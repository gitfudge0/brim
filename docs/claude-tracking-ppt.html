// derived metrics

What we compute from history

Session burn rate

Requests-per-hour from delta between consecutive snapshots.

Δused / Δtime_hrs

Time-to-empty

At current pace, how long until session quota hits 0. Capped at reset time.

remaining / burn_rate

Weekly trend

Plot of seven_day.used across past N weekly cycles.

Session depth

Median + p90 of peak five_hour.used per session over history.

Weekly forecast

4-week median daily usage → project remaining % at end of week. Needs ≥2 weeks of data.

Per-model split

Distribution across Opus / Sonnet / Haiku from historical model buckets.

// new cli surface

Three command changes

NEW  brim history [provider]

Sparkline trend + computed metrics for the past 7 days (or --days N). All enabled providers, or one.

brim history claude brim history --days 30

EXTEND  brim json --history

Machine-readable metrics under a history key. Composable with existing consumers.

brim json claude --history

EXTEND  brim status

Inline burn rate + time-to-empty for the current session. One line added to existing status render.

// delivery

5-phase plan

1
Metrics engine — crates/core/src/history.rs

Pure functions: burn_rate, time_to_empty, weekly_peaks, model_split. Input: &[UsageSnapshot]. No I/O, fully testable.

2
DB helper — snapshots_for_history(provider, days)

One new method on Database. Filters to strategy="oauth_usage" to skip fallback stubs. Reuses snapshots_in_range.

3
brim history command — crates/cli/src/commands/history.rs

DB → metrics → terminal render. Sparklines via Unicode block chars (no new deps). Supports --days, --json.

4
Inline burn rate in brim status

Query last ~2h of snapshots, compute burn rate, append to existing status output. One-liner addition.

5
brim json --history flag

Extend existing json command with a history key when the flag is passed. Reuses phase-1 metrics engine.
