1 · Situation: what we already have

History is already accumulating. Every brim sync writes a full UsageSnapshot JSON blob to usage_snapshots in SQLite. The DB already has snapshots_in_range(provider, from, to). There is no new storage primitive needed — we query what's there.

SQLite history

Already exists
Per-model data
five_hour window broken down per model in the OAuth API response
Missing
History commands
No CLI surface to query, compute, or display trends from stored snapshots

2 · What data Claude exposes

Fields available per sync from GET /api/oauth/usage:

FieldWindowNotes
five_hour.used5-hour sessionRequests used in current session window
five_hour.limit5-hour sessionSession cap (varies by plan)
five_hour.percent_remaining5-hour sessionDirect from API, 0–100
five_hour.resets_at5-hour sessionRFC3339 timestamp of next reset
seven_day.used7-day rollingWeekly premium request count
seven_day.limit7-day rollingWeekly cap
seven_day.percent_remaining7-day rollingDirect from API
seven_day.resets_at7-day rollingWhen the weekly window rolls over

plan, tier—Subscription name/tier ("Claude" / "Pro")
subscriptionType—From local credentials file as fallback
The API is marked experimental. Limit values and model keys may change. Build with that in mind — use Option everywhere, degrade gracefully, and label derived metrics as derived.

3 · Derived metrics worth computing

Session burn rate

Requests-per-hour within the current or recent 5-hour window. Computed from the delta between two consecutive snapshots divided by elapsed time.

burn_rate = Δused / Δtime_hours
// e.g. 3.2 req/hr for this session

Session time-to-empty

At current burn rate, how long until the 5-hour session quota hits 0. Capped at the session reset time (meaningless to project past it).

tte = remaining / burn_rate
// "~1h 20m at current pace"

Weekly consumption trend

Plot of weekly used across past N 7-day windows. One data point = the used value at the start of each weekly cycle.

Typical session depth

Median and p90 of five_hour.used at the peak of each historical session. Tells you how hard you actually push sessions vs. the limit.

Weekly forecast

Using rolling 4-week median daily usage, project remaining % at end of current week. Only shown when ≥2 weeks of history exist. Labeled derived.

Per-model split

Distribution of session usage across Opus / Sonnet / Haiku from historical model buckets. Useful for seeing which model is actually eating quota.

4 · Storage changes

No new tables needed. All metrics are computed on-the-fly from existing snapshots. The only addition is one index to make range queries fast as history grows. 

-- Add to migrate() if not already present
CREATE INDEX IF NOT EXISTS idx_snapshots_provider_strategy
  ON usage_snapshots(provider, strategy, fetched_at DESC);

-- Allows efficient filtering to only oauth_usage snapshots for Claude
-- (skips local_credentials fallback rows that have no bucket data)

The existing prune_after_days config (default 30) already limits unbounded growth. History commands should respect this — no point computing trends over data that's been pruned.

5 · New CLI commands

brim history [provider] new

Shows a sparkline trend of usage over the past 7 days (or N days with --days N), plus computed metrics.

brim history claude
brim history claude --days 30
brim history           # all enabled providers

brim json --history extend

Machine-readable version. Returns metrics as a JSON object alongside current usage. Composable with existing brim json consumers.

brim json claude --history

brim status enhancements extend

Add one line to the existing status output: burn rate and time-to-empty for the current session. No new command needed — these are the most actionable numbers and belong alongside current %.

7 · Phased delivery

1
Metrics engine in brim_core

New file crates/core/src/history.rs — pure functions: burn_rate, time_to_empty, weekly_peaks, model_split. Input: &[UsageSnapshot]. Output: a HistoryMetrics struct. No I/O, fully testable.

2
DB query helper in brim_storage

One new method on Database: snapshots_for_history(provider, days) → Vec<UsageSnapshot>. Filters to strategy = "oauth_usage" so fallback stubs don't pollute metrics. Reuses existing snapshots_in_range.

3
brim history CLI command

New crates/cli/src/commands/history.rs. Calls DB → metrics → renders terminal output. Sparklines via Unicode block chars (no deps). Respects --days, --json.

4
Inline burn rate in brim status

Extend existing status command to show burn rate + time-to-empty for the current session by querying the last ~2h of snapshots. One-liner addition to the status render path.

5
brim json --history

Extend the existing json command to include a history key when the flag is passed. Reuses the same metrics engine from phase 1.

8 · Open questions for you

Q1 — TUI panel?

The app has a crates/tui. Should the history sparkline also appear in the TUI, or is the CLI output enough for now? TUI means a Ratatui chart widget; more work but more interactive.

CLI first (default) TUI panel too TUI only

Q2 — History window default

What's the default lookback for brim history? 7 days aligns with the Claude weekly window. 30 days shows longer trends but needs more history to accumulate first.

7 days (default) 30 days Always show all retained data

Q3 — Scope: Claude only or all providers?

Codex and Copilot also store snapshots. The metrics engine would work generically, but each provider exposes different bucket names. Start Claude-only and generalise later, or build generic from the start?

Claude first, generalise later Generic from the start

Q4 — Burn rate freshness

Burn rate is only useful when there are recent snapshots (last 1–2h). If the most recent snapshot is old, should we show burn rate as stale/unavailable, or always show whatever we can compute?

Hide if latest snapshot >2h old Show with stale label

ponytail: no new storage tables, no new deps — block chars cover sparklines, existing DB query covers history retrieval. Add TUI chart only if Q1 says yes.
